### 3.3 SKU 映射方法

CSV 中：

```
00001
00002
00003
```

数据库中：

```
SKU-00001
SKU-00002
SKU-00003
```

正确的查询键生成方式：

```
mapped_sku_id = "SKU-" + sku_ref.strip()
```

应用前必须验证原始 `sku_ref` 符合五位数字格式，例如使用：

```
re.fullmatch(r"\d{5}", sku_ref.strip())
```

如果编号格式非法，不得静默补零、截断或猜测其他映射方式。应给出明确的输入验证错误。

对于格式合法但数据库中不存在的 SKU，必须保留该输入记录，并标记为“库中缺失”。

已验证的映射基线：

- 直接相等匹配：0 条；
- 使用 `SKU-` 前缀映射：115 条；
- 库中缺失：5 条；
- 缺失编号为 `00031`、`00057`、`00084`、`00099`、`00113`；
- 映射后一对一，没有重复目标。

报告的 `sku_ref` 必须保留 CSV 原始值，不能用 `SKU-xxxxx` 覆盖。

### 3.4 商品处置状态

必须先查询商品是否存在，再判断商品状态：

1. 查询不到对应商品：`库中缺失`；
2. 查询到商品且 `is_deleted == 1`：`已下架`；
3. 查询到商品且 `is_deleted == 0`：`正常评估`；
4. 如果状态值不是预期的 `0` 或 `1`，应明确报错，不能自动把任意非零值解释为已下架。

已确认的数据基线：

| 指标                 | 数量 |
| -------------------- | ---- |
| 清单读取数           | 120  |
| 在库数（包含已下架） | 115  |
| 已下架数             | 5    |
| 库中缺失数           | 5    |
| 正常评估数           | 110  |

注意：`is_deleted=1` 对应题目所说“已下架”，是依据字段名、取值及题目语境作出的高置信度实现假设，并未得到业务方单独确认。请按此假设实现，并在 README 中如实说明。

只有“正常评估”商品可以进入规则引擎。

已下架和缺失商品不得被默认标记为“合规”。

### 3.5 合规规则匹配契约

一条规则只有在三个条件同时满足时才生效。

**条件一：类目匹配**

- 将 `applies_to_category` 按英文逗号 `,` 分割；
- 每个 token 去除首尾空格；
- 商品 `category` 必须与某个 token 完全相等；
- 不允许使用类目子串匹配。

**条件二：材质匹配**

- `material_keyword` 为 `NULL`、空字符串或纯空白时，视为不限材质；
- 其他情况下按竖线 `|` 分割关键词；
- 每个关键词去除首尾空格；
- 商品 `material` 只要包含任意一个有效关键词，即满足材质条件；
- 保持原始大小写语义，不做无依据的大小写转换；
- 如果字段非空却拆分不出任何有效关键词，应将其视为规则数据错误，明确报错。

**条件三：产地匹配**

- `origin_keyword` 为 `NULL`、空字符串或纯空白时，视为不限产地；
- 否则商品 `origin.strip()` 必须与 `origin_keyword.strip()` 完全相等；
- 不得使用产地子串匹配。

三个条件必须同时满足：

```
类目匹配 AND 材质匹配 AND 产地匹配
```

真实风险字段为 `severity`，当前合法值只有：

- `待确认`
- `违规`

风险优先级：

```
违规 > 待确认 > 合规
```

其中，“合规”不是数据库规则等级，而是没有任何规则命中时的默认评估结果。

请遵循：

1. 没有规则命中：风险标记为 `合规`，依据规则填 `—`；
2. 命中一条规则：记录该规则编号；
3. 命中多条规则：风险标记取最严等级，但必须保留全部生效规则编号；
4. 全部命中规则编号按 `rule_id` 升序排列，多个编号以英文分号 `;` 连接；
5. 存在未知风险值时明确报错，不得静默降级；
6. 规则表为空时应报告规则配置错误，不得把所有商品自动判为合规；
7. 缺失和下架商品不执行任何规则评估。

### 3.6 人民币价格换算契约

人民币换算公式：

```
人民币价格 = 商品原价 × exchange_rates.rate_to_cny
```

必须从真实 SQLite 数据库读取汇率，不允许硬编码汇率值。

实际汇率：

| 币种 | 数据库汇率 |
| ---- | ---------- |
| CNY  | 1.0        |
| EUR  | 7.78       |
| JPY  | 0.0476     |
| KRW  | 0.0052     |
| USD  | 7.12       |

真实含义是：

```
1 单位对应币种 = rate_to_cny 单位人民币
```

金额计算要求：

- 使用 Python `Decimal`；
- 使用 `Decimal(str(value))` 将数据库读出的数值转换为十进制表示；
- 使用 `ROUND_HALF_UP` 保留两位小数；
- 输出时固定显示两位小数，例如 `712.00`；
- 不使用倒数；
- 不在代码中硬编码数据库汇率；
- 不擅自修改原价或汇率；
- 缺少汇率、价格非法或汇率异常时必须明确报错；
- 即使当前数据库数据干净，也应对异常输入设计测试。

本题只明确要求对“正常评估”的商品换算人民币价格。因此，已下架和库中缺失的商品不进行人民币换算。

JPY、KRW 商品的换算金额可能很低，但这不能成为修改原始数据的依据。按数据库实际数据严格换算，并在踩坑与验收说明中记录这一观察。

## 四、正式确定的报告口径

报告必须严格满足原始 `instructions.md` 的三个必需部分。

### 4.1 明细区

每个输入记录一行，共 120 行。

建议字段：

| 字段       | 要求                               |
| ---------- | ---------------------------------- |
| `sku_ref`  | CSV 原始 SKU 编号                  |
| `batch_no` | CSV 原始批次号，便于追溯           |
| 处置结果   | 正常评估 / 库中缺失 / 已下架       |
| 商品名     | 商品库数据；缺失填 `—`             |
| 类目       | 商品库数据；缺失填 `—`             |
| 材质       | 商品库数据；缺失填 `—`             |
| 产地       | 商品库数据；缺失填 `—`             |
| 原价       | 原始价格 + 币种，例如 `100.00 USD` |
| 人民币价格 | 换算结果，固定两位小数             |
| 风险标记   | 合规 / 待确认 / 违规               |
| 依据规则   | 命中的规则编号，以分号连接         |

字段处理细则：

**正常评估：**

- 保留完整的商品信息；
- 输出原价；
- 输出已换算的人民币价格；
- 输出三档风险之一；
- 输出所有命中规则编号；没有命中时用 `—`。

**已下架：**

- 保留能够从商品库查到的商品信息和原价；
- 不执行规则评估；
- 人民币价格、风险标记、依据规则填写 `—（不适用）`。

**库中缺失：**

- 商品名、类目、材质、产地、原价、人民币价格、风险标记和依据规则均填 `—`；
- 处置结果明确填写 `库中缺失`；
- 原始 SKU 和批次号必须保留。

不得通过输出“合规”来代替“不适用”。

### 4.2 汇总区

必须包含：

- 合规数量；
- 待确认数量；
- 违规数量；
- Top 风险类目。

三档风险数量只统计正常评估商品，并且三档数量之和必须等于 110。

Top 风险类目的统计规则固定如下：

1. 仅统计至少有一件“违规”或“待确认”商品的类目；
2. 每个正常评估 SKU 按最终风险标记只计数一次；
3. 先按违规数量降序；
4. 违规数量相同，再按待确认数量降序；
5. 两者均相同时，按类目名称升序；
6. 最多展示前 5 个；
7. 应同时显示类目的违规数、待确认数和风险商品总数；
8. 如果没有任何风险类目，明确显示没有风险类目。

该排序方式是为满足题目“Top 风险类目”而确定的实现口径，需在 README 中声明，不要描述成题目强制指定的唯一算法。

### 4.3 完整性自检区

显示以下五个数字：

- 清单读取数；
- 在库数；
- 已下架数；
- 缺失数；
- 实际评估数。

“在库数”的正式定义是：能够关联到商品库的输入记录数，包含已下架商品。

必须验证：

```
清单读取数 = 在库数 + 缺失数
在库数 = 已下架数 + 实际评估数
清单读取数 = 缺失数 + 已下架数 + 实际评估数
```

当前应满足：

```
120 = 115 + 5
115 = 5 + 110
120 = 5 + 5 + 110
```

这些数字必须由实际处理结果动态计算，不允许硬编码输出。

如果任何校验失败，不得将报告宣称为成功生成；程序应明确报告失败原因并返回非零退出码。

1. 三个规则条件分别实现，方便独立测试；
2. 类目使用分列后的精确成员匹配；
3. 材质使用关键词子串匹配；
4. 产地使用完全相等匹配；
5. 三个条件必须同时满足；
6. 同时处理 `NULL`、空字符串和纯空白；
7. 拒绝无效规则 token；
8. 未知的 `severity` 必须报错；
9. 对所有规则进行匹配，不得命中一条后提前结束；
10. 规则 ID 排序后返回；
11. 命中多条规则时取最高风险等级；
12. 无规则命中时返回合规；
13. 缺失和已下架商品不得传入实际评估流程，最好使用清晰的分层接口或调用前置条件防止误用。

该模块不能依赖实际数据库连接，这样既能使用真实规则做评估，也能用构造对象进行纯单元测试。

### 5.4 `pricing.py`：独立价格与汇率模块

建议提供：

```
convert_to_cny(price, currency, exchange_rates)
```

或等价的清晰接口。

要求：

3. 采用 `ROUND_HALF_UP` 保留两位小数；
4. 价格与汇率均必须有效；
5. 币种不存在、汇率缺失或汇率无效时明确抛出错误；
6. 不硬编码任何业务汇率；
7. 不直接修改商品对象的原始价格；
8. 不使用外部实时汇率；

函数应返回可供其他模块使用的 `Decimal` 计算结果，而不是直接格式化成面向报告的字符串。小数位展示交给报告层处理。

### 5.5 `processor.py`：业务流程编排

该模块连接数据加载、商品状态判断、规则引擎和价格模块。

建议提供：

3. 不去重、不静默跳过任何清单记录；
4. 先判定缺失，再判定已下架，最后进入正常评估；
5. 已下架商品不调用规则引擎和价格模块；
6. 缺失商品保留对应输入记录；

对于已经确定的缺失商品，必须正常输出“库中缺失”，不能把它当作异常抛弃。
