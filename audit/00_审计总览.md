## 一、结论摘要

本次审计实际读取并核对了两份核心输入：

- `sku_list.csv`：**120 条**记录，表头为 `sku_ref,batch_no`，UTF-8 with BOM、CRLF 换行；`sku_ref` 无空值、无空白、无重复，全部为 5 位数字（00001–00120）。
- `compliance.db`：真实包含 **3 张表**——`sku_info`（**115 行**）、`compliance_rules`（**10 行**）、`exchange_rates`（**5 行**）；无视图；`PRAGMA integrity_check = ok`。

SKU 关联不能按数据字典所说的“直接相等”处理：直接相等匹配 **0/120**；对 `sku_ref` 做 `strip` 后加 `"SKU-"` 前缀，可匹配 **115/120**，剩余 **5 条**恰好是数据库缺失的 5 个编号。

处置基线与三条等式全部成立：

| 指标 | 含义 | 数量 |
|---|---|---:|
| `N_input` | CSV 实际读取记录数（不含表头） | **120** |
| `N_matched` | 可关联到商品库的记录数（含已下架） | **115** |
| `N_deleted` | 清单中 `is_deleted=1` 的已下架商品数 | **5** |
| `N_missing` | 清单中商品库查不到的商品数 | **5** |
| `N_evaluated` | 正常在售、可进入规则评估的商品数 | **110** |

```text
N_input   = N_matched + N_missing              → 120 = 115 + 5   ✅
N_matched = N_deleted + N_evaluated            → 115 = 5 + 110   ✅
N_input   = N_missing + N_deleted + N_evaluated → 120 = 5 + 5 + 110 ✅
```

汇率数据完整：商品实际使用 **CNY / EUR / JPY / KRW / USD** 五种币种，`exchange_rates` 五种全部覆盖，无缺失、无零值/负值、无重复；人民币代码实际为 **CNY**（不是字典写的 `RMB`）。

**总体判断**：数据本身可以支撑第二阶段开发，但材料中存在 4 个会直接导致实现错误的关键差异——`sku_ref` 格式、`is_deleted` 字段、`severity` 字段名、`RMB/CNY` 币种代码；`seed.py` 的核心逻辑全部未实现且存在静默丢失风险。上述问题均已在审计中定位并给出处理口径。

## 二、直接回答审计要求的 12 个问题

### 1. CSV 是否符合题目要求？实际记录数和字段是什么？

**符合。** 实际读取 **120 条**记录（不含表头），表头为 `sku_ref,batch_no`，文件 1,941 字节，UTF-8 with BOM（`utf-8-sig`），CRLF 换行，末尾有换行。

- `sku_ref`：120 条全部非空、无前后空格，格式全部为 `^\d{5}$`，数值范围 1–120，**无重复**。
- `batch_no`：120 条全部非空，格式全部为 `^B\d{7}$`；**9 个批次号重复，涉及 19 条记录**，但对应的是不同 `sku_ref`。
- 结论：记录数与题目“120 个 SKU”一致；批次号重复不等于 SKU 重复，不得据此去重。

### 2. 数据库有哪些真实表？每张表有多少记录？

| 表名 | 记录数 | 主键 | 说明 |
|---|---:|---|---|
| `sku_info` | **115** | `sku_id` | 商品主数据，实际有 8 列（字典漏了 `is_deleted`） |
| `compliance_rules` | **10** | `rule_id` | 合规规则库，风险字段实际叫 `severity` |
| `exchange_rates` | **5** | `currency` | 汇率表，人民币代码为 `CNY` |

无视图、无外键约束。完整字段、类型、NOT NULL、默认值、索引和建表 SQL 见 [02_数据库Schema.md](02_数据库Schema.md)。

### 3. 商品 SKU 应当采用什么映射方式？有多少匹配失败？

采用：**`"SKU-" + sku_ref.strip()`**，并先用 `^\d{5}$` 校验 `sku_ref` 格式。

- 直接相等：匹配 **0/120**。
- 加 `SKU-` 前缀：匹配 **115/120**，失败 **5 条**。
- 失败编号：`00031`、`00057`、`00084`、`00099`、`00113`（CSV 第 32、58、85、100、114 行）。
- 这 5 个编号恰好是 `sku_info` 在 00001–00120 范围内的全部空缺；反向检查也确认 **115 个数据库 SKU 全部出现在清单中**，映射为一对一，无重复目标、无多对一。
- 不能仅凭“匹配数更多”选定前缀方案；格式证据、反向覆盖和一对一关系共同支持该结论。详见 [03_SKU映射审计.md](03_SKU映射审计.md)。

### 4. 如何判断已下架商品？该判断依据是否足够明确？

真实商品表存在 `is_deleted INTEGER NOT NULL DEFAULT 0`：

- 取值只有 `0` 和 `1`；
- `0` 共 **110** 条，`1` 共 **5** 条；
- 5 条 `is_deleted=1` 的商品为 `SKU-00001`～`SKU-00005`，全部出现在清单第 2–6 行。

**判断依据**：映射成功且 `is_deleted = 1` → 已下架。

**置信度说明**：字段名、取值分布与题目“已下架”语境高度一致，足以支撑实现；但数据字典未记录该字段，数据库也没有 `CHECK` 约束或状态说明，因此严格说这是**高置信度推断**，已列入待确认事项 Q1。没有发现其他可表示状态的字段。

### 5. 正常评估、已下架和库中缺失分别如何识别？

按以下顺序判定，保证每条输入恰好落入一种处置：

1. 先做 SKU 映射；映射后在 `sku_info` 中**不存在** → **库中缺失**（5 条）；
2. 存在且 `is_deleted = 1` → **已下架**（5 条），跳过规则评估；
3. 存在且 `is_deleted = 0` → **正常评估**（110 条）。

该顺序可以避免把“缺失”误判为“下架”。完整 120 条逐行状态见 [03_SKU映射审计.md](03_SKU映射审计.md) 与 [异常数据清单.csv](异常数据清单.csv)。

### 6. 真实规则字段名是什么？风险等级的实际取值是什么？

真实字段为：

```text
rule_id, title, applies_to_category, material_keyword, origin_keyword, severity
```

- 风险字段实际叫 **`severity`**，不是字典写的 `risk_level`；
- 实际取值只有两种：**`待确认` 8 条、`违规` 2 条**；无其他取值、无空值；
- `applies_to_category` 使用英文逗号分隔，10 条规则均无空 token、无空格 token；
- `material_keyword` 使用竖线分隔，均无空 token；
- `origin_keyword` 有 **8 条为空字符串**（表示不限），2 条非空（`意大利`、`越南`）；
- 规则涉及的 8 个类目全部能在商品表中找到；10 个材质关键词全部能在至少一种商品材质中命中；2 个产地值均存在；**无悬空引用**。

完整规则表与匹配口径见 [04_规则库审计与业务口径.md](04_规则库审计与业务口径.md)。

### 9. `seed.py` 有哪些可能造成业务错误或验收失败的问题？

核心问题：

1. **第 23 行**直接用 `row["sku_ref"]` 等值查询 `sku_id`，而真实格式需要 `SKU-` 前缀 → **0/120 匹配**；
2. **第 26–28 行**三个 TODO 全部未实现：规则匹配、汇率换算、缺失处理；
3. 风险固定输出 `待补充`，不属于题目允许的 `合规/待确认/违规` 三档；
4. **第 37–38 行** `except Exception: pass` 静默吞掉单条异常，记录可能不进入 `report`，违反“不允许静默丢失”；
5. 完全不处理 `is_deleted`，已下架商品无法标注；
6. 没有规则匹配、规则编号、人民币换算、汇总区、完整性自检；
7. 只 `print` 一条数量，不生成任何报告文件，不满足“一条命令复现报告”；
8. 未校验 CSV 表头、未校验读取数是否为 120、未处理缺失汇率、未使用 `Decimal`；
9. `sqlite3.connect(DB)` 是读写模式，数据库路径错误时会创建一个空库，随后所有查询异常又被静默吞掉，最终可能输出“共 0 条”而不报错。

**可保留的优点**：参数化查询（无 SQL 注入）、`utf-8-sig` 正确读取 BOM、结构简单。第二阶段应重写，不复用其核心逻辑。逐条审查见 [06_材料差异与种子代码审查.md](06_材料差异与种子代码审查.md)。
