# 03 SKU 映射审计

> **目标**：验证 `sku_list.csv.sku_ref` 与 `sku_info.sku_id` 的真实关联方式，统计每种候选方案的匹配结果，并给出每条输入记录的处置基线。
> **数据**：清单 120 条；商品库 115 条。
> **结论**：采用 `strip` 后加 `"SKU-"` 前缀；匹配 **115/120**，缺失 **5**；映射一对一，无重复目标。

---

## 一、输入侧事实

### 1. `sku_list.csv`

| 项目 | 实测 |
|---|---|
| 记录数 | **120**（不含表头） |
| 字段 | `sku_ref`, `batch_no` |
| 编码/换行 | UTF-8 with BOM；CRLF；末尾有换行 |
| `sku_ref` 格式 | 120/120 为 `^\d{5}$` |
| `sku_ref` 范围 | 数值 1–120（显示为 00001–00120） |
| `sku_ref` 空值/空白/前后空格 | 0 / 0 / 0 |
| `sku_ref` 重复 | **0**（120 个不同值） |
| `batch_no` 重复 | **9 个值重复，涉及 19 条记录**（详见下文） |
| 畸形行 | 0 |

### 2. `sku_info`

| 项目 | 实测 |
|---|---|
| 记录数 | **115** |
| `sku_id` 格式 | 115/115 为 `SKU-` + 5 位数字（模式 `AAA-99999`） |
| `sku_id` 范围 | `SKU-00001`～`SKU-00120`，但不是连续 120 个 |
| 主键重复 | 0 |
| 空值 | 0 |

### 3. 格式差异的直接证据

```text
CSV 示例     ：00001
数据库示例   ：SKU-00001
```

这不是“值不同”，而是**同一编号的两种表示**：CSV 省略了固定前缀 `SKU-`。数据字典也确认 `sku_id` 的格式为 `SKU-xxxxx`，但其第 4 节“`sku_ref` 即 `sku_id`，按此关联即可”与真实数据不符。

---

## 二、候选映射方案与实测结果

对 120 条清单逐条执行四种候选转换，再与 115 个主键做精确匹配：

| 候选 | 映射方式 | 匹配数 | 未匹配数 | 匹配率 | 重复目标 | 结论 |
|---|---|---:|---:|---:|---:|---|
| A | `sku_ref` 直接等于 `sku_id` | **0** | 120 | 0% | 0 | 不可用 |
| B | `strip(sku_ref)` 后加 `"SKU-"` 前缀 | **115** | **5** | **95.83%** | 0 | **采用** |
| C | `strip` + 数字补足 5 位 + `"SKU-"` 前缀 | 115 | 5 | 95.83% | 0 | 与 B 等价；无必要 |
| D | `strip` + 转大写后直接等于 `sku_id` | 0 | 120 | 0% | 0 | 不可用 |

### 候选 A（直接相等）

- 成功匹配：**0 条**。
- 未匹配：**120 条**（全部）。
- 具体未匹配 SKU：`00001`～`00120` 全部。
- 结论：数据字典第 4 节的关联方式与真实数据不符；直接实现会让所有商品查不到。

### 候选 B（前缀映射，采用）

- 成功匹配：**115 条**。
- 未匹配：**5 条**：`00031`、`00057`、`00084`、`00099`、`00113`。
- 匹配到的数据库主键：115 个，无重复目标。
- 成功匹配的完整 `sku_ref` 列表（115 个）见本文附录 A。
- 结论：可用，且 5 条未匹配正好对应数据库中的 5 个编号空缺。

### 候选 C（补零后加前缀）

- 成功匹配：115 条；未匹配：5 条；与 B 完全相同。
- 因为输入全部已经是 5 位数字，补零没有实际作用。
- **不采用**：对非 5 位输入做自动补零，可能把格式异常静默“修正”，不利于发现坏数据；应显式校验格式。

### 候选 D（大写后直接相等）

- 成功匹配：0 条；未匹配：120 条。`SKU-` 前缀不是大小写问题。

### 为什么最终选 B，而不是“匹配数最多的方案”

匹配数最多只是必要条件，不足以证明映射正确。B 还通过了以下反向验证：

1. **格式证据**：数据库 115 个主键全部为 `SKU-` + 5 位数字；CSV 120 个值全部为 5 位数字，差异恰好是固定前缀。
2. **反向覆盖**：把 CSV 全部转换后，**115 个数据库主键全部被清单覆盖**，没有“库中有、清单没有”的商品；说明不是只匹配到一部分的偶然结果。
3. **缺失对应**：未匹配的 5 条，正好是 `00001–00120` 中数据库缺少的 5 个编号；不是零散、无规律的失败。
4. **一对一**：`sku_ref` 无重复、`sku_id` 是主键、转换函数单值；没有一对多或多对一。
5. **字典佐证**：字典对 `sku_id` 格式（`SKU-xxxxx`）的描述与数据库一致，仅关联方式写错。

因此 B 是基于数据证据的确定性映射，不是因为“能多匹配几条”而猜测的规则。

## 三、映射规范（第二阶段直接采用）

```python
# 伪代码：只表达契约，不是本轮的业务程序
def to_sku_id(sku_ref: str) -> str:
    s = sku_ref.strip()
    if not re.fullmatch(r"\d{5}", s):
        # 不得静默补零/截断；应记为格式异常，并按“库中缺失”或显式错误处理
        raise ValueError(f"unexpected sku_ref format: {sku_ref!r}")
    return "SKU-" + s
```

约定：

- **保留原始 `sku_ref`** 用于报告第一列；`SKU-xxxxx` 只作为查询键，不覆盖原始值。
- `strip` 只用于消除潜在前后空格；本数据无空格，规范化不改变结果。
- 非 5 位数字：不得静默补零或截断；应显式记录异常，避免把坏数据伪装成正常匹配。
- 映射失败：处置结果必须是 **库中缺失**，不得丢弃、不得当作下架。
- 后续若出现重复 `sku_ref`：每行独立处理，不能按 `sku_ref` 去重；当前数据无重复。

## 六、完整状态基线

按“先缺失、再下架、否则正常”的顺序，120 条全部有且只有一种处置：

| 状态 | 数量 | 说明 |
|---|---:|---|
| 匹配成功（含下架）`N_matched` | **115** | 映射后能在 `sku_info` 找到 |
| 已下架 `N_deleted` | **5** | 匹配成功且 `is_deleted=1` |
| 库中缺失 `N_missing` | **5** | 映射后找不到 |
| 正常评估 `N_evaluated` | **110** | 匹配成功且 `is_deleted=0` |
| **输入合计 `N_input`** | **120** | CSV 实际读取数 |

### 三条等式

```text
N_input   = N_matched + N_missing               → 120 = 115 + 5
N_matched = N_deleted + N_evaluated             → 115 = 5 + 110
N_input   = N_missing + N_deleted + N_evaluated → 120 = 5 + 5 + 110
```

三条全部成立。逐行台账见 [sku_mapping.csv](sku_mapping.csv)（120 行，含行号、原始 `sku_ref`、映射键、处置结果、商品字段）。
