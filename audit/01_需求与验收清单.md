## 一、题目明确规定（业务规定）

以下内容直接来自 `instructions.md`，属于实现与验收的硬约束。

### 1. 输入文件、字段与预期记录数

| 项目 | 规定 |
|---|---|
| 输入文件 | `sku_list.csv` |
| 预期记录数 | **120 个 SKU** |
| 字段 | `sku_ref`（待检商品的 SKU 标识）、`batch_no`（批次号，仅记录用） |
| 其他输入 | `compliance.db`、`data-dictionary.md`（AI 生成，未人工校对）、`seed.py`（AI 生成，仅供参考） |

### 2. 每个 SKU 需要关联的数据库信息

每个清单 SKU 需关联 `sku_info` 商品主数据，取得：

- 商品名 `name`
- 类目 `category`
- 材质 `material`
- 产地 `origin`
- 原价 `price`
- 币种 `currency`
- 商品状态（是否已下架）

正常评估的商品还需使用：

- `compliance_rules`：按类目/材质/产地匹配规则，得到风险标记与规则编号；
- `exchange_rates`：按商品币种取得 `rate_to_cny`，换算人民币价格。

### 3. 三类处置结果的区别

| 处置结果 | 定义（题目口径） | 是否评估规则 | 是否换算价格 |
|---|---|---|---|
| **正常评估** | 清单 SKU 能关联到商品库，且商品正常在售 | 是 | 是 |
| **已下架** | 清单 SKU 能关联到商品库，但商品已下架 | 否，跳过规则评估 | 题目未要求；只要求“正常评估的商品”换算 |
| **库中缺失** | 清单 SKU 在商品库中查不到 | 否 | 否 |

**硬要求**：三类必须显式标注；库中缺失不得静默丢弃；每条形如 `sku_ref` 都必须有且只有一种处置。

### 4. 合规规则的匹配条件（题目 2.1）

一条规则对某 SKU **生效**，当且仅当以下三个条件**同时满足**：

1. **类目**：SKU 的 `category` 出现在规则的 `applies_to_category`（英文逗号分隔）中；
2. **材质**：规则的 `material_keyword` 为空，或 SKU 的 `material` 包含其中任一竖线分隔的关键词；
3. **产地**：规则的 `origin_keyword` 为空，或 SKU 的 `origin` 与该值相同。

### 5. 多条规则同时命中时如何确定最终风险等级

- 生效规则的风险等级即该 SKU 的标记；
- 命中多条时取**最严**：**违规 > 待确认**；
- 没有任何规则命中 → **合规**。

### 6. 价格换算的币种、汇率来源与精度

- 目标币种：**人民币（CNY）**；
- 汇率来源：`exchange_rates.rate_to_cny` 的**数据库实际值**，不得硬编码示例汇率；
- 公式：`人民币价格 = 商品原价 × 对应币种的 rate_to_cny`；
- 精度：保留 **2 位小数**；
- 只要求“正常评估的商品”做价格换算。

### 7. 最终合规报告必须包含的内容

报告格式不限（Markdown / CSV / HTML 均可），但必须包含三个部分：

#### ① 明细区（每个 SKU 一行）

| 字段 | 要求 |
|---|---|
| `sku_ref` | 清单中的 SKU 标识 |
| 处置结果 | 正常评估 / 库中缺失 / 已下架 |
| 商品名、类目、材质、产地 | 来自商品库；缺失商品填“—” |
| 原价 | 标价 + 币种 |
| 人民币价格 | 换算后，2 位小数 |
| 风险标记 | 合规 / 待确认 / 违规 |
| 依据规则 | 规则编号；多条用分号分隔；合规且无规则命中填“—” |

#### ② 汇总区

- 合规 / 待确认 / 违规各档数量；
- **Top 风险类目**。

#### ③ 完整性自检区

五个数字：

1. 清单读取数
2. 在库数
3. 已下架数
4. 缺失数
5. 实际评估数

**必须对得上账**：五个数字之间的关系要能自洽。

### 8. 四项交付要求（缺一视为不完整）

1. **可运行的完整代码**；
2. **README**：环境依赖、运行方式（评测者一条命令能跑起来并复现报告）、设计要点；
3. **AI 使用记录**：与 AI 协作过程的导出（对话记录 / 截图 / 操作日志，形式不限，但必须真实、可对应到产出）；
4. **一页《踩坑与验收说明》**：过程中发现了什么问题（包括材料里的）、怎么发现的、怎么处理的。

### 9. 全部验收条件

| # | 验收条件 | 判定方式 |
|---|---|---|
| A1 | 全部 **120 个 SKU** 在报告中有明确处置（三选一） | 明细行数 = 120；每行处置 ∈ {正常评估, 库中缺失, 已下架}；无空值 |
| A2 | 每个**正常评估**的 SKU 有三档风险标记之一，并引用规则编号 | 风险 ∈ {合规, 待确认, 违规}；非“合规”必须有规则编号；合规且无命中填“—” |
| A3 | 人民币价格换算正确（以数据库实际数据为准） | 逐条复算 `原价 × rate_to_cny`，2 位小数；汇率来自 DB |
| A4 | 完整性自检五个数字真实、自洽 | 读取数=120；读取数=在库数+缺失数；在库数=已下架数+实际评估数 |
| A5 | 评测环境**一条命令**可复现 | README 给出单条命令；干净环境运行后生成同一份报告 |

### 10. 期限与使用规则

- 期限：发卷起 **7 天**；
- 允许并鼓励使用任何 AI 工具；
- “仅与 AI 问答的经历”不构成得分项，评分看**产出与过程记录**。

## 二、真实数据事实（本轮实测，不是题目规定）

以下数据用于把上述业务规定落到可执行的实现口径。完整证据见 [02](02_数据库Schema.md)～[06](06_材料差异与种子代码审查.md)。

### 1. CSV 实测

| 项目 | 实测结果 |
|---|---|
| 路径/大小 | `sku_list.csv` / 1,941 字节 |
| 编码 | UTF-8 with BOM（`utf-8-sig`），CRLF，末尾有换行 |
| 表头 | `sku_ref,batch_no`（2 列） |
| 记录数 | **120**（与题目一致） |
| `sku_ref` | 全部 5 位数字，00001–00120；无空值、无空白、无前后空格、**无重复** |
| `batch_no` | 全部 `B` + 7 位数字；无空值；**9 个值重复，涉及 19 条记录**，但对应不同 SKU |
| 畸形行 | 无（无缺列/多列） |

### 2. 数据库实测

| 表 | 行数 | 真实关键字段 | 备注 |
|---|---:|---|---|
| `sku_info` | **115** | `sku_id, name, category, material, origin, price, currency, is_deleted` | 比字典多 `is_deleted` |
| `compliance_rules` | **10** | `rule_id, title, applies_to_category, material_keyword, origin_keyword, severity` | 风险字段是 `severity`，不是 `risk_level` |
| `exchange_rates` | **5** | `currency, rate_to_cny` | 人民币代码是 `CNY`，不是 `RMB` |

- `sku_info` 的 8 个类目全部出现；14 种材质；8 个产地；5 种币种；
- `is_deleted`：0 有 110 条，1 有 5 条（`SKU-00001`～`SKU-00005`）；
- `price`：全部为正的有限实数，范围 14.21–415.97；
- 规则 `severity`：8 条待确认、2 条违规；
- 汇率：CNY 1.0、EUR 7.78、JPY 0.0476、KRW 0.0052、USD 7.12；无缺失/零值/负值。

### 3. SKU 映射实测

| 候选方式 | 匹配数 | 未匹配 | 结论 |
|---|---:|---:|---|
| 直接相等 | 0/120 | 120 | 不可用 |
| `strip` + `"SKU-"` 前缀 | **115/120** | **5** | **采用** |
| `strip` + 数字补 5 位 + 前缀 | 115/120 | 5 | 等价，但无必要 |
| `strip` + 大写后直接相等 | 0/120 | 120 | 不可用 |

缺失 5 条：`00031`（第 32 行）、`00057`（第 58 行）、`00084`（第 85 行）、`00099`（第 100 行）、`00113`（第 114 行）。

### 4. 处置基线实测

```text
N_input     = 120
N_matched   = 115   （含已下架 5 条）
N_deleted   = 5
N_missing   = 5
N_evaluated = 110
```

三条等式全部成立，详见 [03_SKU映射审计.md](03_SKU映射审计.md)。

## 三、题目未明确、需要决策的事项

以下内容**不能**从现有文件直接推出唯一答案；第二阶段必须先在 README/设计中写死口径。

| ID | 待确认事项 | 为什么不能直接确定 | 建议口径 | 是否需要出题方确认 |
|---|---|---|---|---|
| Q1 | `is_deleted=1` 是否等价于“已下架” | 字典遗漏该字段；无 CHECK 约束；只能依据字段名与分布推断 | 按 `1=已下架` 实现，README 记录依据 | 建议确认 |
| Q2 | 完整性自检的“在库数”是 115 还是 110 | 题目只给名称，未给公式；“可关联”与“在售”都说得通 | 在库数=可关联含下架=115；同时展示 110 与等式 | **需要明确**（呈现口径） |
| Q3 | 保留 2 位小数的舍入方式 | 题目未说明 HALF_UP / 银行家舍入 | `Decimal` + `ROUND_HALF_UP` | 可在 README 声明 |
| Q4 | 缺失/已下架行的金额、风险、规则列填什么 | 题目只规定缺失商品的名称等填“—” | 缺失全填“—”；已下架保留商品信息/原价，金额/风险/规则填“—（不适用）” | 可在 README 声明 |
| Q5 | Top 风险类目的排序指标、Top N | 题目未定义 | 违规数降序→待确认数降序→类目名，前 5 | 可在 README 声明 |
| Q6 | JPY/KRW 价格量级是否合理 | 换算后金额极低，但题目只要求按 DB 汇率换算 | 照常换算，不修改数据；在踩坑说明记录 | 建议确认 |

> 注意：Q2 不是“数据问题”，而是**报告口径问题**。如果不写清定义，即使数字都真实，也可能被验收者认为“五个数字对不上账”。

## 四、需求与验收的逐条落地映射

| 需求/验收 | 第二阶段实现位置（建议） | 验收方式 |
|---|---|---|
| 读取 120 条，保留原始 `sku_ref` | 加载模块 `loader` | 断言读取数=120；输出原始值 |
| `SKU-` 前缀映射，缺失显式标记 | 映射函数 + 状态判定 | 单测覆盖 115/5；缺失 5 条逐条断言 |
| 已下架跳过规则 | 状态分支 | 5 条 `is_deleted=1` 不进入规则引擎 |
| 三条件规则匹配 | 规则引擎 | 单测覆盖类目/材质/产地/组合/空值 |
| 多规则取最严 | 规则引擎聚合 | 构造 违规+待确认 命中，断言违规 |
| 无命中=合规 | 规则引擎聚合 | 构造无命中，断言合规 |
| 人民币换算 2 位 | 价格模块 | 5 种币种各取样例复算；断言 Decimal |
| 明细区 120 行 | 报告模块 | 行数、列、缺失填“—” |
| 汇总区三档 + Top 类目 | 报告模块 | 合计=110；Top 口径写入 README |
| 完整性自检五数 | 报告模块 | 断言三条等式 |
| 一条命令复现 | README + 入口脚本 | 干净环境执行并比对报告 |
| AI 记录、踩坑说明 | 过程材料 | 对话记录/日志与产出对应 |

## 五、本阶段明确“不做”的事

为避免越界，本轮没有做以下工作：

- 没有实现逐 SKU 的完整规则判定程序；
- 没有计算三档风险的最终数量；
- 没有生成最终《跨境商品合规检查报告》；
- 没有修改 `seed.py`、`data-dictionary.md`、`sku_list.csv`、`compliance.db`；
- 没有向数据库写入任何数据。

本阶段的产出只覆盖：需求、Schema、映射、规则口径、汇率条件、材料差异、数量基线。
