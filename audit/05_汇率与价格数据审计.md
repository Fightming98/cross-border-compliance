## 四、金额计算规范（第二阶段实现契约）

### 1. 公式与方向

```text
人民币价格 = 商品原价 × 对应币种的 rate_to_cny
```

- `rate_to_cny` 的含义是“1 单位该币种 = 多少人民币”，与公式方向一致；
- 不得使用倒数，不得硬编码示例汇率；
- 汇率必须从 `exchange_rates` 按 `currency` 查询得到；
- 人民币商品使用 `CNY` 行（1.0），不是 `RMB`。

### 2. 精度

题目只规定“保留 2 位小数”，未规定舍入模式。建议实现：

```python
from decimal import Decimal, ROUND_HALF_UP

price = Decimal(str(row["price"]))      # 不要用 Decimal(float)
rate = Decimal(str(row["rate_to_cny"])) # 读取数据库实际值
cny = (price * rate).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
```

理由：

- 直接用二进制 `float` 相乘再 `round()` 可能出现 `0.1` 类表示误差；
- Python 内置 `round()` 使用银行家舍入（round-half-even），与常见财务“四舍五入”不同；
- `Decimal(str(x))` 保留数据库值的十进制表示，适合金额计算；
- 不要用 `Decimal(178.97)`（会带入二进制展开）。

> 舍入模式属于题目未明确项（Q3）；若出题方要求银行家舍入，应改为 `ROUND_HALF_EVEN` 并同步更新测试。当前建议在 README 中明确写出 `ROUND_HALF_UP`。

### 3. 异常处理

| 场景 | 处理 |
|---|---|
| 商品币种在汇率表缺失 | **显式失败**，指出 SKU 与币种；不得跳过该商品 |
| 汇率为 NULL/0/负数/非有限 | **显式失败**，视为数据错误 |
| 商品价格为 NULL/0/负数/非有限 | **显式失败**；当前数据均为正 |
| 币种大小写/空格不一致 | 不建议静默 `upper()` 掩盖；应先报数据异常；当前数据干净 |
| 已下架/缺失商品 | 不要求换算；人民币价格填“—（不适用）”，但不得伪装成 0 |

### 4. 第二阶段必测用例

1. 五种币种各取一条，按公式复算，断言 2 位小数；
2. CNY 使用 1.0，结果等于原价（保留 2 位）；
3. 构造 `price=0.005`、`rate=1` 等边界，验证 HALF_UP 行为；
4. 构造 `price=1.005`，确认不会出现浮点 `1.00` 误差；
5. 删除某个币种汇率，断言程序显式报错而不是静默跳过；
6. 汇率置 0/负数，断言报错；
7. 商品币种为 `RMB`（不存在于汇率表），断言报错并提示实际应为 `CNY`；
8. 已下架/缺失商品不进入价格模块；
9. 全量 110 条正常评估商品均有非空人民币价格；
10. 汇总校验：人民币价格列无 `NaN`、无 `Infinity`、无负值。

## 五、结论

1. 汇率表 5 行完整，商品 5 种币种全部覆盖；不存在无法换算的商品。
2. 人民币代码是 **CNY**，不是字典写的 `RMB`。
3. 公式方向明确：`原价 × rate_to_cny`，保留 2 位。
4. 价格与汇率均无零值/负值/非有限值；当前没有价格数据阻断项。
5. 舍入方式题目未规定，建议 `Decimal + ROUND_HALF_UP` 并写入 README。
6. JPY/KRW 换算后金额量级异常偏低，属于业务合理性观察，不影响按题目公式换算；需业务确认，不得自行修改数据。
