# 跨境商品合规检查助手

读取 120 条待检 SKU 清单，关联 SQLite 商品库，按规则库判定合规风险、按数据库汇率换算人民币价格，并生成一份可追溯的 Markdown《跨境商品合规检查报告》。

本实现基于第一阶段审计结论，**没有沿用 `seed.py` 的未完成逻辑**；原始输入文件与 `audit/` 审计产物均未被修改。

## 1. 功能概览

- 读取带 UTF-8 BOM 的 `sku_list.csv`，保留全部 120 条原始记录与 `batch_no`；
- 以只读方式打开 `compliance.db`，读取商品、规则与汇率三张表；
- 将 `sku_ref` 规范化为 `SKU-` + 五位数字，无法关联的记录显式标记“库中缺失”；
- 按“缺失 → 已下架 → 正常评估”的顺序判定处置结果；
- 正常评估商品执行三条件规则匹配，多规则命中取最严，输出全部规则编号；
- 使用数据库实际汇率与 `Decimal + ROUND_HALF_UP` 换算人民币价格；
- 生成 120 行明细、三档风险汇总、Top 风险类目和完整性自检区；
- 写报告前后执行完整性校验与落盘复核，失败时返回非零退出码。

## 2. 环境与依赖

- Python **3.10+**（实际验证环境：Python 3.12.4）；
- 仅使用 Python 标准库；
- 无第三方依赖，`requirements.txt` 中已注明。

## 3. 一条命令运行

在项目根目录执行：

```bash
python main.py
```

默认读取：

- `sku_list.csv`
- `compliance.db`

默认输出：

- `reports/compliance_report.md`

### 可选参数

```bash
python main.py --csv sku_list.csv --db compliance.db --output reports/compliance_report.md
python main.py --expected-count 120
```

- `--csv`：输入清单路径；
- `--db`：SQLite 数据库路径；
- `--output`：报告输出路径（父目录会自动创建）；
- `--expected-count`：期望记录数，默认 `120`；正式验收必须保持默认值。

退出码：

- `0`：处理、校验、报告生成与落盘复核全部成功；
- `1`：输入/数据库/规则/价格/完整性/报告错误，或发生未预期异常。

| `main.py` | 默认路径、命令行参数、流程串联、错误处理与退出码 |

## 6. 关键业务口径

### 6.1 SKU 映射

```text
mapped_sku_id = "SKU-" + sku_ref.strip()
```

- `sku_ref` 必须匹配 `^\d{5}$`，否则显式报错；
- 不补零、不截断、不猜测；
- 报告保留 CSV 原始 `sku_ref` 与 `batch_no`；
- 当前基线：120 条中 115 条可关联，5 条库中缺失。

### 6.2 商品状态

判定顺序固定为：

1. 数据库中不存在：`库中缺失`；
2. 存在且 `is_deleted == 1`：`已下架`；
3. 存在且 `is_deleted == 0`：`正常评估`；
4. 其他 `is_deleted` 取值：显式报错。

只有“正常评估”商品进入规则引擎和价格模块。已下架/缺失商品不会被标记为“合规”。

### 6.3 规则匹配

一条规则生效当且仅当：

```text
类目匹配 AND 材质匹配 AND 产地匹配
```

- 类目：`applies_to_category` 按英文逗号拆分、逐项 `strip` 后**精确成员匹配**；
- 材质：`material_keyword` 为 `NULL`/空串/纯空白时视为不限；否则按 `|` 拆分，任一关键词为商品材质**子串**即通过；
- 产地：`origin_keyword` 为 `NULL`/空串/纯空白时视为不限；否则与 `origin.strip()` **完全相等**；
- 风险优先级：`违规 > 待确认 > 合规`；
- 命中多条规则时保留**全部**规则编号，按 `rule_id` 升序，用英文分号 `;` 连接；
- 未知 `severity`、空类目、空 token、空规则表均显式报错。

### 6.4 人民币换算

```text
人民币价格 = 商品原价 × exchange_rates.rate_to_cny
```

- 汇率只从数据库读取，不硬编码；
- 使用 `Decimal(str(value))`；
- 使用 `ROUND_HALF_UP` 保留 2 位小数；
- CNY 也使用数据库中的 `CNY` 行（当前为 `1.0`）；
- 缺少汇率、价格/汇率非法时显式报错，不跳过商品；
- 已下架/缺失商品不换算。

### 6.5 完整性口径

- **在库数** = 能够关联到商品库的输入记录数，**包含已下架**；
- 五个数字由实际处理结果动态计算，不硬编码；
- 三条等式：

```text
清单读取数 = 在库数 + 缺失数
在库数 = 已下架数 + 实际评估数
清单读取数 = 缺失数 + 已下架数 + 实际评估数
```

当前正式数据应满足：

```text
120 = 115 + 5
115 = 5 + 110
120 = 5 + 5 + 110
```

### 6.6 Top 风险类目

题目未规定唯一算法，本项目固定为：

1. 仅统计至少有一件“违规”或“待确认”商品的类目；
2. 每个正常评估 SKU 按最终风险只计一次；
3. 违规数降序；
4. 违规数相同则待确认数降序；
5. 仍相同则类目名升序；
6. 最多 5 个；
7. 同时显示违规数、待确认数、风险商品总数；
8. 没有风险类目时明确显示“没有风险类目”。

## 7. 待确认事项的实现假设

第一阶段审计提出的 Q1–Q6 在本实现中的处理如下。以下均为**实现假设**，不是已经获得业务方书面确认的事实。

| ID | 假设 |
|---|---|
| Q1 | `is_deleted=1` 按“已下架”处理；依据字段名、取值分布和题目语境推断 |
| Q2 | “在库数”= 可关联记录数（含已下架）= 115；同时展示 110 与三条等式 |
| Q3 | 保留 2 位小数采用 `ROUND_HALF_UP` |
| Q4 | 缺失商品相关字段填“—”；已下架商品保留商品信息和原价，人民币价格/风险/规则填“—（不适用）” |
| Q5 | Top 风险类目采用上述固定排序，取前 5 |
| Q6 | JPY/KRW 金额偏低按数据库原值照常换算，不修改数据；在踩坑说明中记录 |

## 10. 已知限制与数据观察

1. `is_deleted` 与“已下架”的语义是推断的，README 与验收说明已明确标注；
2. JPY/KRW 商品按数据库汇率换算后金额很低（如 KRW 商品约 0.45–2.13 CNY），疑似合成数据或单位问题；未修改任何原价或汇率；
3. 原数据字典有 4 个实质性差异（`risk_level`/`severity`、遗漏 `is_deleted`、`RMB`/`CNY`、`sku_ref` 直接关联），本实现以真实数据库为准；
4. 当前输出为 Markdown；如后续需要网页展示，可在稳定的报告模型之上增加一层只读 UI，而不改动业务模块；
5. 第三阶段已完成独立审查、缺陷修复和逐 SKU 对账；共修复 5 个 P1、2 个 P2 问题，最终 121 个测试全部通过，详见 `docs/第三阶段代码审查与修复报告.md`。
